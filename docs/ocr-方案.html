充电截图识别 · 方案思考

目标：把充电小程序 / 滴滴的支付完成页截图，快速变成「冲充电」里的一条记录。只做方案，不实施。
结论
纯前端 OCR（Tesseract.js 本地运行）+ 字段级抽取 + 人工确认

理由：不离开现有 PWA、截图不出设备、无需后端。SOC / 里程不指望截图，走「待补充」机制单独闭环。OCR 只负责"候选值"，绝不自动保存。

1问题拆解

数据源 A · 支付完成页截图
充电度数、金额、充电时间/时长、站点。这是 OCR 的目标，但不同 App 的版式、字体、字段名差异极大。
数据源 B · 车辆 App
充电前 / 后 SOC、里程表读数。截图里通常没有，需要手动补录，或未来用系统能力桥接。

三个硬约束：① 字段识别必须"宁缺毋错"，错了比没有更糟；② 截图含金额、位置、时间等敏感信息，优先本地处理；③ 现有项目是纯前端、无构建、资源全本地，方案不能依赖后端。

2方案对比

方案识别质量隐私落地成本结论
A. 纯前端 OCR
Tesseract.js + WASM		 中上，依赖版式与预处理 最佳 截图不出设备 低，不改架构；需内置引擎与语言包 推荐 v1

C. 后端 OCR 服务 高，可用商业 API 差 截图上传第三方 中，需后端与密钥 不推荐
D. 手动 + 智能默认 靠人 最佳 极低 兜底 所有方案的最后一环

推荐 A 的原因：现有 PWA 不加壳就能上线，识别在浏览器内完成；配合 D 的人工确认，准确率问题被"用户核对"兜住。B 留作以后做 App 壳时的升级路径。

3处理管线

关键点：OCR 引擎懒加载（点"截图识别"才下载，约 10–20MB），识别过程在 Worker 中跑，不阻塞页面；识别结果只作为表单预填，不自动保存。

4字段抽取规则

字段抽取策略置信度与校验
充入电量 (\d+(?:\.\d+)?)\s*(?:度|kWh|千瓦时)，并优先取"充电量 / 充电度数"标签附近的数字 范围 1–200 度；与金额互算单价 0.5–3.0 元/度，异常则标红
金额 (?:¥|￥|实付|金额|费用)\s*[:：]?\s*(\d+(?:\.\d+)?)，取"实付"优先，避免把度数当金额 范围 0.5–500 元；与电量互算单价
日期 (\d{4})\s*[-/年.]\s*(\d{1,2})\s*[-/月.]\s*(\d{1,2})；只有时分时默认取今天 缺失不报错，UI 标注"默认今天"，允许改
时长 / 站点 (\d+)\s*(?:分钟|min|小时|h)、运营商关键词 可选字段，不参与核心校验
SOC 前后 默认不识别。若截图恰好含 (\d{1,3})\s*%\s*(?:→|至|-)\s*(\d{1,3})\s*% 可作为候选，但标记"需核对" 来源应为车辆 App，截图识别只作参考

核心原则：上下文优先于数字。同一屏有 6 个数字时，靠"标签词 + 位置"决定哪个是度数、哪个是金额；抽不准就不填，让用户手输。

5交互流程

  • 入口：记一笔页顶部加「截图识别」按钮；设置页可开关。支持一次多选，进入批量补录模式。
  • 识别中：全屏轻提示"识别中…"，显示进度；失败可重试或手动填写。
  • 确认页：识别结果预填进现有表单（cf_kWh / cf_totalCost / cf_date），低置信字段描红并聚焦第一个；用户逐项核对。
  • 保存：用户点保存才写入；SOC / 里程为空时写入 pendingExtra: true，列表显示「待补充」角标。

6补充信息（SOC / 里程）闭环

本次先做
「待补充」标记 + 详情页一键「补充 SOC / 里程」→ 直接打开已有编辑态。表单里 SOC / 里程保持可见，但文案提示"可在车辆 App 查看后补录"。
以后可做
① 设置页「批量补录」入口，按时间列出待补充记录；② iOS 快捷指令 / 原生壳桥接车辆 App 数据（方案 B）。

7隐私与边界

  • 截图全程在浏览器本地处理，不上传、不存储原图；识别完成即从内存释放。
  • 若将来改为后端 OCR，必须单独征得同意，并明确截图留存策略。
  • 引擎与语言包需要内置到 app/vendor/（项目当前无 CDN 依赖，需保持一致）；首次加载体积是主要代价。
  • 不支持 OCR 的环境（老设备 / 隐私模式限制）直接隐藏入口，保留手动填写。

8风险与对策

风险影响对策
识别错误（度数 / 金额混淆）数据污染，且难发现人工确认强制化 + 单价合理性校验 + 低置信标红
各 App 版式差异大识别率不稳定按"度数 / 金额 / 日期"做模式库；持续收集样本优化规则
中文模型体积大首屏变慢懒加载 + Worker + 本地缓存；识别时才下载
截图含敏感信息隐私顾虑纯前端处理，明确告知"不上传"
SOC / 里程缺失电耗 / 电池分析不完整待补充标记 + 补录入口，不阻塞记账

9落地路线

v1 单图识别纯前端 · 已实施

内置 Tesseract.js + chi_sim；字段抽取 + 人工确认 + 待补充标记。不改架构，可独立上线。

v2 批量补录效率

多选截图逐张识别、逐条确认；待补充记录聚合页；识别样本积累。

v3 原生桥接体验

若做原生壳，用系统 OCR 替代 Tesseract，并尝试车辆 App 数据快捷指令。
